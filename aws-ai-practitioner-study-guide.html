Domain 1 — 31% Foundation Model Integration, Data Management, and Compliance

Exam Focus: This is the largest domain. Expect questions on choosing the right foundation model, managing data for AI workloads, understanding AWS AI/ML services, and ensuring regulatory compliance.

1.1 AI, ML, and Generative AI Concepts

Artificial Intelligence (AI) is the broad field of creating machines that can perform tasks requiring human-like intelligence. Machine Learning (ML) is a subset of AI where systems learn patterns from data rather than being explicitly programmed. Deep Learning is a subset of ML that uses multi-layered neural networks (hence "deep") to model complex patterns.

Foundation Models (FMs) are large-scale models pre-trained on vast datasets that can be adapted to many downstream tasks. Examples include large language models (LLMs) like Amazon Nova, Claude, and Llama. Generative AI refers to models that create new content—text, images, audio, video, or code—rather than just classifying or predicting.

1.2 Types of Data in AI Systems

Data is the fuel for AI. Understanding data types helps you choose the right services and preprocessing steps:

  • Structured data: Tabular formats (CSV, Parquet, SQL tables). Highly organized, easy to query. Used in regression, classification.
  • Unstructured data: Text, images, audio, video. Requires specialized processing. Examples: PDF documents, social media posts, medical images.
  • Semi-structured data: JSON, XML, log files. Has some organization but not rigid schema.
  • Labeled vs. Unlabeled: Labeled data has target values (used for supervised learning). Unlabeled data requires clustering or representation learning.
  • Time-series data: Data points indexed in time order. Critical for forecasting and anomaly detection.
Data Quality Matters: Garbage in, garbage out. Biased, incomplete, or dirty data will produce unreliable models. AWS services like AWS Glue DataBrew and SageMaker Data Wrangler help clean and prepare data.

Domain 2 — 26% Implementation and Integration

2.1 Retrieval Augmented Generation (RAG)

RAG enhances foundation models by retrieving relevant information from external knowledge sources before generating a response. This reduces hallucinations and grounds answers in factual data.

How RAG Works

  1. Ingestion: Documents are chunked, converted to embeddings, and stored in a vector database.
  2. Retrieval: When a user asks a question, it's converted to an embedding and matched against the vector store.
  3. Generation: The retrieved context is appended to the prompt, and the model generates an answer based on both its training and the retrieved facts.

AWS RAG Implementation

  • Amazon Bedrock Knowledge Bases — Fully managed RAG with automatic chunking, embedding, and retrieval. Supports OpenSearch Serverless, Aurora, Neptune, DocumentDB, and RDS for PostgreSQL as vector stores.
  • Amazon Kendra — Enterprise search with semantic understanding, useful for RAG over structured and unstructured enterprise data.

2.2 Prompt Engineering Techniques

Prompt engineering is the art of crafting inputs to get desired outputs from foundation models without changing model weights.

Core Techniques

  • Zero-shot prompting: Ask the model to perform a task with no examples. Best for simple, well-defined tasks.
  • Single-shot / Few-shot prompting: Provide one or a few examples in the prompt to guide the model's behavior. Improves consistency.
  • Chain-of-Thought (CoT): Prompt the model to "think step by step." Dramatically improves reasoning on complex problems.
  • System prompts: Set global behavior instructions (e.g., "You are a helpful medical assistant. Always cite sources.").
  • Negative prompts: Specify what the model should NOT do (e.g., "Do not provide medical advice").
  • Prompt templates: Reusable structured prompts with variables. Essential for production applications.

2.4 Agents and Multi-Step Workflows

Agents are AI systems that can autonomously perform multi-step tasks by reasoning, using tools, and maintaining memory.

Amazon Bedrock Agents

  • Break down user requests into steps.
  • Retrieve information from Knowledge Bases (RAG).
  • Call APIs through Action Groups to perform actions (e.g., book a flight, check inventory).
  • Maintain conversation memory across turns.

Integration Patterns

  • API-based integration: Call Bedrock via AWS SDK or REST API from your application.
  • Event-driven: Use Amazon EventBridge and AWS Lambda to trigger AI processing based on events.
  • Batch processing: Use SageMaker Batch Transform or Bedrock batch inference for large-scale offline processing.
  • Real-time streaming: Use Bedrock streaming APIs for responsive chat interfaces.
Architecture Tip: For customer-facing chatbots, combine Amazon Lex (intent recognition and dialogue management) with Amazon Bedrock (generative responses) for a robust solution that handles both structured interactions and open-ended conversations.

2.5 Cost Tradeoffs and Pricing Models

Understanding pricing helps you design cost-effective solutions:

  • On-demand inference: Pay per token (input + output). Best for variable, unpredictable workloads.
  • Provisioned Throughput: Reserve capacity at a fixed hourly rate. Best for consistent, high-volume production traffic.
  • Custom models: Pay for training time + storage + inference. Training is a one-time cost; hosting incurs ongoing charges.
  • Batch inference: Often cheaper than real-time for large offline jobs.
Cost Optimization: Use smaller models where possible, cache responses for repeated queries, implement request throttling, and monitor with AWS Cost Explorer and CloudWatch. Consider using AWS Inferentia for cost-effective inference at scale.

Domain 3 — 20% AI Safety, Security, and Governance

Exam Focus: Questions on securing AI systems, responsible AI practices, bias detection, transparency, and governance frameworks.

3.1 Securing AI Systems

AI systems require defense-in-depth security across multiple layers:

Identity and Access Management

  • IAM Roles and Policies: Use least-privilege access. Bedrock operations require specific IAM permissions (bedrock:InvokeModel, bedrock:CreateKnowledgeBase).
  • Resource-based policies: Control access to specific Bedrock resources.
  • VPC Endpoints / AWS PrivateLink: Keep traffic between your VPC and Bedrock off the public internet.

Data Protection

  • Encryption at rest: S3, EBS, and databases use AWS KMS-managed keys (SSE-KMS).
  • Encryption in transit: TLS 1.2+ for all API communications.
  • Amazon Macie: Uses ML to discover and classify sensitive data in S3 (PII, PHI, financial data).

Application Security

  • Prompt Injection: Malicious inputs designed to override system instructions. Mitigate with input validation, Guardrails, and output filtering.
  • Model Extraction: Attempts to steal model weights through repeated queries. Mitigate with rate limiting and monitoring.
  • Data Poisoning: Corrupting training data to compromise model behavior. Mitigate with data validation and anomaly detection.

3.2 Responsible AI Principles

Responsible AI ensures systems are fair, transparent, safe, and accountable:

Key Dimensions

  • Fairness: Models should not discriminate against protected groups. Test for disparate impact across demographics.
  • Inclusivity: Systems should work equitably for all users, regardless of language, ability, or background.
  • Robustness: Models should perform reliably under varying conditions and adversarial inputs.
  • Safety: Prevent harmful outputs (toxicity, hate speech, dangerous instructions).
  • Veracity: Ensure outputs are truthful and grounded in evidence.
  • Transparency: Users should understand when they're interacting with AI and how decisions are made.
  • Privacy: Protect personal data and comply with regulations.

AWS Tools for Responsible AI

  • Guardrails for Amazon Bedrock — Content filtering (denied topics, word filters, PII redaction), safety controls, and contextual grounding checks.
  • Amazon SageMaker Clarify — Detects bias in data and models; explains model predictions.
  • SageMaker Model Monitor — Detects data drift and model quality degradation in production.
  • Amazon Augmented AI (A2I) — Human-in-the-loop review for model predictions requiring human judgment.
  • SageMaker Model Cards — Document model intended uses, limitations, and performance metrics.
Environmental Consideration: Training large models consumes significant energy. AWS offers tools like the Customer Carbon Footprint Tool and recommends using efficient instances (Inferentia, Trainium) to reduce environmental impact.

3.3 Governance and Compliance Frameworks

Governance ensures AI systems align with organizational values and legal requirements:

Governance Strategies

  • Data Lifecycles: Define retention, archival, and deletion policies. Use S3 Lifecycle policies and AWS Backup.
  • Logging and Monitoring: CloudTrail for API auditing, CloudWatch for metrics and alarms, Config for configuration tracking.
  • Data Residency: Ensure data stays in specific geographic regions. AWS Regions and Local Zones help enforce this.
  • Review Cadence: Regular audits of model performance, bias metrics, and security posture.

Generative AI Security Scoping Matrix

A framework for categorizing GenAI use cases by risk level:

  • Low risk: Internal productivity tools (e.g., code suggestions, document summarization).
  • Medium risk: Customer-facing content generation with human review.
  • High risk: Automated decisions affecting individuals (e.g., credit scoring, hiring, medical diagnosis).
Best Practice: Establish an AI Governance Board with representatives from legal, security, data science, and business units. Define clear escalation paths for high-risk AI deployments.

3.4 Explainability and Transparency

Stakeholders need to understand how AI systems arrive at decisions:

  • Transparent models: Decision trees, linear regression offer inherent interpretability.
  • Black-box models: Deep neural networks and LLMs require post-hoc explanation techniques.
  • SageMaker Clarify provides SHAP (SHapley Additive exPlanations) values to explain feature importance.
  • Model Cards document intended use, limitations, training data, and performance metrics.
  • Open-source models (e.g., Llama) offer greater transparency into architecture and training data than proprietary models.
Tradeoff: More interpretable models (e.g., linear models) are often less accurate than complex models (e.g., transformers). Choose the right balance based on regulatory requirements and use case criticality.

Domain 4 — 12% Operational Efficiency and Optimization for GenAI Applications

Exam Focus: Questions on optimizing performance, cost, latency, and scaling GenAI workloads on AWS.

4.1 Performance Optimization

Optimizing GenAI applications involves balancing speed, accuracy, and cost:

Inference Optimization Techniques

  • Model Distillation: Train a smaller "student" model to mimic a larger "teacher" model. Reduces latency and cost with minimal accuracy loss.
  • Quantization: Reduce model precision (e.g., FP32 → INT8) to speed up inference and reduce memory.
  • Caching: Cache frequent queries and responses. Use ElastiCache or CloudFront for response caching.
  • Streaming: Use streaming APIs to return tokens as they're generated, improving perceived latency.
  • Batching: Group multiple requests to maximize GPU utilization.

Infrastructure Optimization

  • AWS Inferentia2 / Trainium2: Purpose-built silicon for cost-effective inference and training.
  • Auto Scaling: Use SageMaker endpoints with auto-scaling policies based on invocation metrics.
  • Multi-AZ Deployment: Deploy across Availability Zones for high availability.
  • Edge Deployment: Use AWS IoT Greengrass or SageMaker Edge Manager for low-latency edge inference.
Latency vs. Cost: Provisioned Throughput offers predictable latency but requires capacity planning. On-demand is flexible but can have variable latency during peak times. For user-facing applications, Provisioned Throughput is usually worth the cost.

4.2 MLOps and Production Readiness

MLOps (Machine Learning Operations) brings DevOps practices to ML workflows:

Key MLOps Practices

  • Experiment Tracking: Log hyperparameters, metrics, and artifacts. SageMaker Experiments helps organize trials.
  • CI/CD for ML: Automate training pipelines with SageMaker Pipelines and AWS CodePipeline.
  • Model Versioning: Track model versions with SageMaker Model Registry.
  • A/B Testing: Deploy multiple model versions and route traffic gradually. SageMaker supports shadow deployments and canary releases.
  • Monitoring: Track data drift, concept drift, and model quality with SageMaker Model Monitor and CloudWatch.
  • Automated Retraining: Trigger retraining pipelines when drift thresholds are breached.

Production Checklist: Before deploying to production, ensure you have rollback procedures, monitoring dashboards, alerting thresholds, data validation, and a human review process for high-stakes predictions.

4.3 Scaling and Availability

AWS provides multiple strategies for scaling GenAI workloads:

  • Horizontal Scaling: Add more instances behind a load balancer. Use SageMaker multi-model endpoints or serverless endpoints.
  • Vertical Scaling: Use larger instance types (e.g., ml.p4d for GPU-heavy workloads).
  • Serverless Inference: SageMaker Serverless Endpoints automatically scale from zero—ideal for intermittent traffic.
  • Multi-Region: Deploy across Regions for global availability and disaster recovery. Use Route 53 for geo-routing.
  • Throttling and Quotas: Understand AWS service quotas (e.g., Bedrock TPS limits) and implement client-side backoff.
Scaling Pitfall: Cold starts in serverless endpoints can add latency. For latency-sensitive applications, keep a minimum number of warm instances using Provisioned Concurrency or traditional endpoints with auto-scaling minimums.

5.2 Troubleshooting Common Issues

Production AI systems encounter predictable failure modes:

Data Issues

  • Data Drift: Input data distribution changes over time (e.g., seasonal patterns, new product categories). Detect with SageMaker Model Monitor.
  • Concept Drift: The relationship between inputs and outputs changes (e.g., customer preferences evolve). Requires model retraining.
  • Missing Values: Handle through imputation, deletion, or model-specific techniques.
  • Label Quality: Noisy labels degrade model performance. Use Amazon A2I for human verification.

Model Issues

  • Overfitting: Model memorizes training data, performs poorly on new data. Mitigate with regularization, more data, or simpler models.
  • Underfitting: Model is too simple to capture patterns. Mitigate with more complex architectures or feature engineering.
  • Hallucinations: Model generates false information. Mitigate with RAG, grounding, and fact-checking.
  • Bias: Systematic errors favoring certain groups. Detect with Clarify and mitigate with balanced datasets and fairness constraints.

Infrastructure Issues

  • Throttling: Exceeding service quotas. Monitor with CloudWatch and implement exponential backoff.
  • Cold Starts: Delay when scaling from zero. Use provisioned capacity or keep-alive pings.
  • Memory Errors: Models exceeding instance memory. Use smaller batches, quantization, or larger instances.
Debugging Workflow: When a model degrades in production, check (1) data pipeline health, (2) recent data drift, (3) infrastructure metrics, (4) model version changes, (5) external factors (holidays, campaigns).

5.3 Validation Strategies

Validation ensures models generalize to unseen data:

  • Train/Validation/Test Split: Typical splits are 70/15/15 or 80/10/10. Never tune hyperparameters on the test set.
  • Cross-Validation: K-fold cross-validation provides robust performance estimates, especially with small datasets.
  • Holdout Sets: Reserve a temporally recent holdout set for time-series problems.
  • A/B Testing: Compare model versions in production with real users. Measure business metrics, not just technical ones.
  • Shadow Deployment: Run new model alongside production model without affecting users. Compare outputs before switching traffic.
Leakage Warning: Data leakage occurs when information from outside the training set influences the model. Common causes: preprocessing on the full dataset before splitting, including future information in time-series, or duplicate records across splits.
